# v0.1.2 repair and playability plan

## Request and supported scenario

- **User-reported symptoms:** devices show no usable interaction prompt/response; textures render incorrectly.
- **Target supplied by the user:** Minecraft Bedrock **26.2**, hosted multiplayer/Realm, with a player able to build a trap and capture either another player or a mob.
- **Compatibility guardrail:** retain the stable Script API (no Beta APIs experiment required) and the existing declared minimum engine version unless a verified compatibility defect requires changing it.
- **Verification honesty:** repository tests can validate pack structure, script behavior through mocks, resource references, and the archive. They cannot render assets or simulate a real Realm/client input path. Those checks remain explicit in the test handoff.

## Work plan

### 1. Trace the placement-to-interaction route

1. Confirm the custom item places the expected anchor block.
2. Confirm the placement event converts that block into the corresponding registered device entity.
3. Confirm each entity exposes a player interaction component and the stable `playerInteractWithEntity` event routes to its registered device.
4. Exercise empty-hand feedback, reinforcement, teammate rescue, and the existing automatic capture lifecycle in tests.
5. Verify player and mob capture paths remain distinct and unaffected by the interaction repair.

### 2. Make interactions discoverable and responsive

1. Replace the raw interaction prompt with a localized Bedrock action key for touch controls.
2. Restrict the entity interaction trigger to players and keep the server event as the authoritative gameplay handler.
3. Preserve the pre-interaction held item so reinforcement reads the correct hand item, while still verifying that the item remains in the selected slot before consuming it.
4. Give players useful feedback when they use an idle device, try to rescue themselves, reinforce successfully, or try an unsupported action. Do not silently consume unrelated items.
5. Add regression tests through the real entry-point event subscription, not only direct calls to device methods.

### 3. Repair texture/resource mapping

1. Resolve every terrain/item atlas entry to a real PNG in the resource pack; specifically reconcile the `cc_` terrain aliases with the actual block texture filenames.
2. Set each entity/block geometry's declared texture width/height to the dimensions of its referenced PNG so UV coordinates use the intended texture canvas.
3. Check legacy two-number box-UV rectangles against the declared texture bounds; expand the repeatable material atlases where needed and adjust the Reliquary door UV that exceeded the image height.
4. Replace the current narrow color-bar item placeholders with separate transparent, recognizable pixel-art inventory icons for all five devices.
5. Keep the existing entity and block art unless a verified mapping defect requires changing it; avoid speculative texture redesign.

### 4. Prevent the defects from returning

Extend the build validator to check:

- texture files referenced by every terrain/item atlas alias exist;
- block texture aliases resolve to atlas entries and actual PNGs;
- client-entity texture references exist;
- entity geometry texture dimensions agree with their referenced images;
- each interaction component has a localized prompt key;
- manifest, module, dependency, and package versions all agree on v0.1.2.

### 5. Release preparation

1. Update behavior/resource pack manifests, the dev GameTest pack version, npm metadata/lockfile, build output banner, README, changelog, and validation expectations.
2. Keep identifiers, pack UUIDs, saved dynamic-property keys, recipes, and gameplay balance stable to avoid breaking existing worlds.
3. Run syntax checks, stable-API type checking, the full automated gameplay suite, source-reference validation, archive validation, and `git diff --check`.
4. Build a versioned `.mcaddon` containing exactly the behavior and resource `.mcpack` files; inspect the archive contents and package manifests.
5. Push only the Arena session branch and open a PR against `main`.

## Acceptance criteria

- The add-on imports with matching v0.1.2 pack/module/dependency versions and retains the stable API dependency.
- An installed device exposes a useful touch-screen interaction label; the entity interaction event reaches the correct registered device.
- An empty-hand interaction explains automatic capture/reinforcement; an eligible armor item is consumed exactly once when reinforcement succeeds; an occupied device can be rescued by another player, while the captive receives clear self-rescue feedback.
- Existing proximity detection captures eligible survival players and mobs; creative/spectator immunity and existing release/break behavior remain covered by tests.
- Every atlas and entity texture reference resolves to a real PNG; geometry texture dimensions match the referenced image; legacy box-UV bounds remain within the atlas; each item has its own readable icon.
- `npm test`, `npm run typecheck`, `./build.sh`, package validation, and whitespace checks pass.
- The `.mcaddon` is provided to the user for a Bedrock 26.2 multiplayer/Realm test. The PR and handoff clearly distinguish automated validation from in-engine verification.

## User test matrix (Bedrock 26.2 multiplayer/Realm)

1. Import the `.mcaddon`; enable both Cursed Contraptions packs on a **copy** of the test world/Realm first. The shipped packs should not require Beta APIs. Cheats are only needed for optional `/give` or admin commands; survival recipes can be used instead.
2. Confirm all five icons render correctly in inventory, place all five devices, and inspect each model from multiple sides in daylight and shade. There should be no missing-texture checkerboard/purple texture, misplaced UV patches, or blank icon.
3. On touch controls, aim at the device and confirm the localized **Use / Rescue** action appears; tap it. On controller/keyboard, use the normal entity-interact input. An empty-hand interaction should return guidance rather than appearing inert.
4. Hold a vanilla armor piece and interact with an unoccupied device: one piece should be consumed, the reinforcement count/durability should increase, and the device should reject further items at its slot limit without consuming them.
5. Put a survival player and a mob near separate devices. Confirm automatic capture for both; confirm creative/spectator players are not captured. A teammate should be able to rescue a player, and the captive should receive an explanation if they attempt to self-rescue.
6. Watch close/torture/release animations, break a device, verify captive release and exactly one item drop, then leave/rejoin to check Realm persistence/recovery.
7. If any step fails, record the exact Bedrock build, client platform/control method, whether the Realm owner enabled both packs, and the visible Content Log/script error. These observations are required before claiming the live Realm path is verified.
