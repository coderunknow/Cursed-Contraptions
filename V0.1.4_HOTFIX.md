# v0.1.4 hotfixes — creative inventory, then placement

Two defects were found by in-game testing after the v0.1.4 build was published.
Both are fixed in the current asset; the version stays **0.1.4**.

## Defect 1 — "I don't see any item in the game though I activate the add on."

Every item and anchor block declared
`"group": "itemGroup.name.miscellaneous"`. That value is not in the vanilla
creative-group enumerator, and current Bedrock requires the group to be
namespaced (`<namespace>:<name>`, documented value pattern `^(?:.)+:(?:.)+$`),
so the game discarded the whole `menu_category` and dropped all ten entries from
the creative menu.

**Fix.** Items and blocks declare the namespaced group
`cc:itemGroup.name.devices`; `behavior_pack/item_catalog/crafting_item_catalog.json`
defines that group (icon: the Iron Maiden, all ten entries) and `en_US.lang`
labels it *Cursed Contraptions (Devices)*. `tests/validate_build.py` gained a
creative-registration stage that rejects an un-namespaced group, a hidden
category (`none`), a group that no catalog defines, a group that does not list
the declaring identifier, an unknown icon, and a missing localization key.

## Defect 2 — "I see it, but I can't place it."

The device items declared `minecraft:block_placer` at item schema version
**1.21.0**. The documented requirement for that component is a format version of
at least **1.21.50** (Microsoft Learn, item component reference; the Bedrock
Wiki documents the current component as 1.26.0+). Below the minimum the game
loads the item and shows it in the menu, then ignores the placement component,
so using the item does nothing at all — including the crafted device, because
the recipes output the same item.

**Fix.**

1. Items and blocks use the `1.21.60` schema — the same version as the pack's
   `min_engine_version`, so every world that can load the pack reads the
   placement component.
2. Anchor blocks declare `minecraft:geometry: {"identifier":
   "minecraft:geometry.full_block"}` explicitly, matching every documented
   data-driven block example (an implicit geometry is how a failed conversion
   leaves an invisible obstacle, the original v0.1.2 report).
3. The stale `cc:durability` entity default (`100` for every device) is now
   derived from `config.js`: a fresh device has no dynamic properties, so the
   property default *is* its starting durability. Previously every new device
   spawned at 100 of 150–300 and showed wear stages 2–3 immediately.
4. `tests/validate_build.py` gained a placement-chain stage: every
   `block_placer` item must meet the documented minimum version and point at a
   defined block, every anchor block must declare material instances and a
   resolvable geometry, and every device's `cc:durability` default must equal
   its configured `baseDurability`. Both new rules were verified by
   re-introducing the old values (the build fails with a precise message).
5. `npm test` gained a regression test for the fresh-device durability and wear
   contract (39 tests total).

## Verification

- `python3 tools/texturegen/build_assets.py` — writes and verifies all assets.
- `npm test` — **39 tests**, 0 failures.
- `npm run typecheck` — clean against the stable 1.17.0 API surface.
- `tests/validate_build.py` — 0 errors, including the creative-registration and
  placement-chain stages.
- `./build.sh` — packages the `.mcaddon` and validates the archive.
- In-engine: the items must be visible in the creative menu and placeable from
  the creative menu, from a crafted item, and from `/give`. Automated checks
  cannot open the creative inventory or press a place button; see
  `tests/GAMETESTS.md` §7–8.

## Compatibility

No identifier, UUID, recipe, dynamic-property key, entity property name, or
balance value changed. Existing worlds keep their devices, captives, durability,
and reinforcements; the only content differences are where the items are filed
in the creative menu, the item/block schema versions, the entity property
default, and the explicit block geometry.
