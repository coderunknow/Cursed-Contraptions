# v0.1.3 art, containment, and animation plan

## Request and supported scenario

- **User-reported symptoms (all in-game on Bedrock 26.2):**
  1. "Some items cannot be placed — I place them, but they are invisible after
     being placed." Clarified in discussion as *something is there but nothing
     renders* (the obstacle or hitbox exists; no model appears).
  2. "The cage mechanics are still rough, and they make the mobs stutter."
  3. "The objects need more animations and polish."
- **Requested scope decisions:** hand-painted texture work rather than flat
  colours; captive mobs should struggle but stay contained instead of being
  frozen solid; device balance may change if the result is better.
- **Compatibility guardrail:** retain the stable Script API (no Beta APIs
  experiment required), `min_engine_version [1, 21, 60]`, `@minecraft/server`
  1.17.0, and every existing identifier, pack UUID, dynamic-property key,
  entity property, tag, and recipe so existing worlds keep working.
- **Verification honesty:** repository checks can validate pack structure,
  script behavior through mocks, resource references, and the archive. They
  cannot render assets or drive a real client input path. Those limits are
  stated in the handoff and in `tests/GAMETESTS.md`.

## Root causes found

1. **Invisible models.** All shipped textures were grayscale or indexed-colour
   PNGs (colour type 0/3/4). Bedrock binds only true-colour images to entity
   models; the entity spawned, kept its collision box, and rendered nothing —
   matching the report exactly.
2. **Invisible anchor block.** The placeable block referenced
   `geometry.cc_iron_maiden_block`, which was never generated, so a device that
   failed to convert left a fully invisible obstacle. The conversion itself
   could silently fail (single attempt, one tick later, no retry, no restore).
3. **Item icons could not resolve.** The item atlas keyed aliases by device
   slug while items requested `cc_item_<slug>`; the icons were also a generic
   placeholder rectangle.
4. **Mob stutter.** Containment teleported the captive onto the seat every five
   ticks and re-asserted its lock constantly, fighting the mob's own AI.
5. **Missing animation coverage.** Four devices had no `detecting`/`released`
   controller states, so those transitions could not be shown in game.

## Work plan

### 1. Make every placed device visible

1. Repaint all five entity atlases as 8-bit RGBA pixel art with per-device
   palettes, keeping every UV inside its declared atlas.
2. Replace the broken anchor geometry with plain full-cube blocks that have a
   painted side texture, and delete the stale model and duplicate block files.
3. Harden placement: retry with backoff while the chunk loads, accept whichever
   contraption anchor sits at the position, refuse to stack devices, and restore
   the anchor block if the entity cannot be created.
4. Publish item atlas aliases that match the item component, and paint five
   readable 16x16 inventory icons.

### 2. Make caged mobs struggle without stuttering

1. Hold mobs with Slowness VII plus Blindness, refreshed once a second with
   particles disabled; no custom entity definitions are needed for vanilla mobs.
2. Never teleport a captive that is still inside its drift window; correct at
   most once a second and only after a genuine escape attempt.
3. Keep the "struggle" read: occasional strain animation, dust puff, and a frame
   rattle when the device is struck.
4. Keep players movement-locked, restore their original permission exactly
   once, and clear stale capture tags on join and chunk load.

### 3. More animation and polish

1. Generate nine animations per device, including `detect`, `closed`, `strain`,
   `open`, and `released`, with a controller in which every state can reach
   every other state.
2. Align animation lengths with gameplay timings (capture delay, close, closed
   pause, torture interval, release).
3. Add feedback: impact sparks, capture/release bursts, a hit rattle, and
   localized messages for reinforcement, rescue, and self-rescue refusal.
4. Make devices static fixtures (no gravity, no collision) so they cannot sink
   through unloaded floors or push a captive out of its seat.

### 4. Prevent the defects from returning

1. Reject non-RGBA textures in `tests/validate_build.py`.
2. Delete stale generated/duplicate files during every asset build.
3. Keep the existing placement, containment, rescue, reinforcement, durability,
   recovery, admin-command, and end-to-end tests green, and keep `checkJs`
   type-checking clean against the stable 1.17.0 typings.

### 5. Release preparation

1. Update both manifests, npm metadata/lockfile, the build banner, README,
   changelog, and validation expectations to v0.1.3.
2. Keep identifiers, pack UUIDs, dynamic-property keys, and recipes stable.
3. Run the automated suite, type checking, source validation, whitespace
   checks, and `./build.sh`, then inspect the packaged `.mcaddon`.
4. Push only the Arena session branch and open a PR against `main`.

## Acceptance criteria

- Placing any of the five devices always leaves a visible device in the world.
  A failed conversion restores the anchor block instead of vanishing silently.
- No shipped texture is anything other than 8-bit RGBA, and the validator
  enforces it.
- A captured mob struggles (strain animation plus dust) but does not visibly
  stutter, and a captured player cannot walk out of the device.
- Every device has nine animations and a controller that can display each
  device state, including `detecting`, `released`, and the strain overlay.
- `npm test`, `npm run typecheck`, `./build.sh`, package validation, and
  whitespace checks pass.
- The handoff and PR distinguish automated validation from in-engine
  verification; no live rendering or input claim is made without a client test.

## User test matrix (Bedrock 26.2)

1. Import the `.mcaddon` on a **copy** of the test world/Realm; enable both
   packs. Beta APIs are not required. Cheats are only needed for `/give` or
   admin commands.
2. Confirm all five inventory icons render, then place all five devices and
   check that each model appears immediately, from several angles, in daylight
   and in shade. None should be invisible, purple, or checkerboarded.
3. Capture a mob with each device: the mob should stay inside, occasionally
   struggle, and not judder or clip through the frame.
4. Capture a player: movement should stay locked, a teammate should be able to
   open the device, and the captive should be freed and moved clear.
5. Watch the full animation cycle (detect → close → closed → torture → open →
   released → idle), hit a device to see the rattle/sparks, reinforce one with
   armor, break one and confirm exactly one item drop and a freed captive.
6. If any step fails, record the Bedrock build, platform/controls, whether the
   owner enabled both packs, and the Content Log/script error text.
